## `KeyListener` Is Just an Interface

You already know how interfaces work from your IO project: `ArmIO` listed what an arm can do, and `ArmIOTalonFX` **implemented** it.

Java's `KeyListener` is the same kind of contract. It says "**I can react to keyboard keys**," and it lists three methods:

| Method | When Java calls it |
|---|---|
| `keyPressed(KeyEvent e)` | The moment a key goes **down** |
| `keyReleased(KeyEvent e)` | The moment a key comes back **up** |
| `keyTyped(KeyEvent e)` | When a key produces a **character** (like `a` or `?`, but not arrow keys) |

So this line from Step 3:

```java
public class Main implements KeyListener {
```

means "`Main` signs the `KeyListener` contract." And that's why Step 3 has two methods that do nothing:

```java
@Override
public void keyReleased(KeyEvent e) {
    // Not used
}

@Override
public void keyTyped(KeyEvent e) {
    // Not used
}
```

Your `ArmIO` gave every method a `default` body, so `new ArmIO() {}` worked with nothing inside the braces. `KeyListener` **doesn't** have default bodies, so you must write all three, even the ones you don't need. A contract is a contract! You have to show up, even if all you do is stand there. 🧍

And each one gets `@Override`, just like `toString()` in Module 3. If you misspell `keyPresed`, `@Override` catches it. Without it, the typo would silently become a brand-new method that **nobody ever calls**, and your keys would just... not work. 😩

## Giving Java Your Phone Number: `addKeyListener(this)`

```java
frame.addKeyListener(this);
```

Signing the contract isn't enough. The window also needs to know **who** to call when a key is pressed. That's what this line does. But who are we handing over? `this`!

In the Java Classes lessons, `this.name` meant "**my** field called name." Here, `this` all by itself means "**me, the whole object**." So the line reads:

> "Hey window, when a key is pressed, call **me**. I signed the KeyListener contract, so you know I have a `keyPressed` method."

Without this line, the window has no idea anyone cares about the keys, and your `keyPressed` method never runs. (It's like signing up for a job but never giving them your phone number. 📵)

## Figuring Out Which Key: `KeyEvent`

When Java calls `keyPressed`, it hands you a `KeyEvent` object named `e`. It's like a little **delivery slip** 📦 describing what happened.

```java
@Override
public void keyPressed(KeyEvent e) {
    int keyCode = e.getKeyCode();

    switch (keyCode) {
        case KeyEvent.VK_UP:
            robot.moveUp();
            break;
        case KeyEvent.VK_DOWN:
            robot.moveDown();
            break;
        case KeyEvent.VK_LEFT:
            robot.moveLeft();
            break;
        case KeyEvent.VK_RIGHT:
            robot.moveRight();
            break;
    }
}
```

- `e.getKeyCode()` returns an **int**: a number that identifies which key was pressed.
- Nobody wants to memorize that the up arrow is `38`. So Java gives every key a **named constant**: `KeyEvent.VK_UP`, `KeyEvent.VK_W`, `KeyEvent.VK_SPACE`, and so on. `VK` stands for "**V**irtual **K**ey." (They're `public static final int`s, just like the constants in our robot's constants file.)
- Then it's a plain `switch` on an `int`.

| Key | Constant |
|---|---|
| ↑ ↓ ← → | `VK_UP`, `VK_DOWN`, `VK_LEFT`, `VK_RIGHT` |
| Letters | `VK_A` to `VK_Z` |
| Numbers | `VK_0` to `VK_9` |
| Spacebar, Enter, Escape | `VK_SPACE`, `VK_ENTER`, `VK_ESCAPE` |

### Where these come from

```java
import java.awt.event.KeyEvent;
import java.awt.event.KeyListener;

import javax.swing.JFrame;
import javax.swing.SwingUtilities;
```

- `java.awt.event` is the **events** shelf of Java's library: things that happen, like key presses.
- `javax.swing` is the **window** shelf: frames, panels, labels.

## The Starting Line: `invokeLater`

```java
public static void main(String[] args) {
    System.out.println("Program started!");
    SwingUtilities.invokeLater(() -> new Main());
}
```

Swing has **one special helper** in charge of everything about the window, called the *Event Dispatch Thread*. Think of it as the **one waiter** in a restaurant who's allowed to serve the windows. 🍽️ If anyone else tries to build or change a window, things can get mixed up.

`invokeLater` means "**Waiter, please do this job when you're ready.**"

The job is `() -> new Main()`. You know that arrow from your arm commands: it's a **lambda**, a tiny nameless function, just like `() -> setState(state)` inside your `InstantCommand`. Here it means "**a job that does: `new Main()`**."

So the whole line reads: "Waiter, when you're ready, build a new `Main`."

> 💡 You'll see this exact `invokeLater` line at the bottom of almost every Swing program. It's fine to treat it as "the magic words that start a Swing app."

### `Main` is set up like `RobotContainer`

```java
Main() {
    robot = new Robot();
    frame = new JFrame();
    // ...set up the window...
    frame.addKeyListener(this);
}
```

Up until now, `main` did all the work. Now `main` just builds a `Main` object, and **`Main`'s constructor** builds the robot and the window and wires up the key listener. `robot` and `frame` are fields, so `keyPressed` can reach `robot` later.

Sound familiar? It's the same pattern as `RobotContainer`: its constructor creates your subsystems and binds your controller buttons, then the events take it from there.

## 🙈 Common Oopsies

- **Leaving out one of the three methods.** You'll get an error like `Main is not abstract and does not override abstract method keyTyped(KeyEvent) in KeyListener`. Translation: "you broke the contract!" Add the missing method, even if it's empty.
- **Forgetting `frame.addKeyListener(this);`** The contract is signed, but nobody gave the window your phone number. Nothing happens when you press keys.
- **Forgetting to click the window.** Keys only go to the window with focus.
- **Misspelling a method name** without `@Override`, for example `keypressed`. It compiles but never runs.
- **Forgetting `break`** in a `case`. Pressing ↑ would move up **and** down! (Remember fall-through from Module 3.)
