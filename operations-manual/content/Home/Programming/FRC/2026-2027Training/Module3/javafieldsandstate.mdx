## The Backpack Analogy

So far, our robot has **skills** (methods), but it forgets everything right after each one finishes. Variables made *inside* a method vanish when the method ends, like writing on a whiteboard that gets erased after every class. 🧽

**Fields** are variables that belong to the *object itself*. Think of them as the robot's **backpack** 🎒. Whatever's in the backpack stays there for the robot's whole life, and **every method** of the robot can reach into it.

Each robot gets its **own** backpack. If you build two robots, moving one doesn't move the other.

The values in an object's fields at any moment are called its **state**. ("Where is it? How fast? How much battery?")

## The Real Code (Step 3)

Here's the Step 3 robot. It now remembers its position on a grid:

```java
class Robot {
    int x;
    int y;

    public void moveUp() {
        y = y - 1;
        System.out.println("Moving UP - New position: (" + x + ", " + y + ")");
    }

    public void moveDown() {
        y = y + 1;
        System.out.println("Moving DOWN - New position: (" + x + ", " + y + ")");
    }

    public void moveLeft() {
        x = x - 1;
        System.out.println("Moving LEFT - New position: (" + x + ", " + y + ")");
    }

    public void moveRight() {
        x = x + 1;
        System.out.println("Moving RIGHT - New position: (" + x + ", " + y + ")");
    }

}
```

### Fields live *inside the class* but *outside any method*

`int x;` and `int y;` sit at the top of the class, not inside a method. That's what makes them fields. Every method below them can use `x` and `y`.

### Default values

We never wrote `x = 0`, so what's in `x` at the start? Fields get **automatic default values**:

| Type | Default |
|---|---|
| `int`, `double` | `0` / `0.0` |
| `boolean` | `false` |
| `String` (and other objects) | `null` (meaning "nothing here yet") |

So a brand-new Step 3 robot starts at `(0, 0)`.

> ⚠️ This is **only** true for fields. A variable inside a method has *no* default, and Java will refuse to compile if you use it before giving it a value.

### Wait, why does "up" make `y` *smaller*?

On a computer screen, `(0, 0)` is the **top-left corner**, and `y` counts **down** the screen, like line numbers on a page. Moving up means going to a smaller line number. You'll see this for real in Module 5 when the robot gets a window.

### Building strings with `+`

```java
"Moving UP - New position: (" + x + ", " + y + ")"
```

When `+` has a String on either side, it **glues** things together (Module 1 called this *concatenation*). Numbers get turned into text automatically, so this prints something like `Moving UP - New position: (0, -1)`.

## Leveling Up: Step 4's Robot

Step 4 polishes the robot with some pro moves:

```java
class Robot {
    private int x;
    private int y;
    private final int stepSize;

    public Robot() {
        x = 250;
        y = 250;
        stepSize = 10;
    }

    public void moveUp() {
        y -= stepSize;
        System.out.println("Moving UP - New position: (" + x + ", " + y + ")");
    }

    public void moveDown() {
        y += stepSize;
        System.out.println("Moving DOWN - New position: (" + x + ", " + y + ")");
    }

    public void moveLeft() {
        x -= stepSize;
        System.out.println("Moving LEFT - New position: (" + x + ", " + y + ")");
    }

    public void moveRight() {
        x += stepSize;
        System.out.println("Moving RIGHT - New position: (" + x + ", " + y + ")");
    }

    public int getX() {
        return x;
    }

    public int getY() {
        return y;
    }

    @Override
    public String toString() {
        return "Robot at position (" + x + ", " + y + ")";
    }
}
```

Let's unpack the new stuff.

### The constructor sets the starting state

```java
public Robot() {
    x = 250;
    y = 250;
    stepSize = 10;
}
```

Remember, the constructor is the **birth moment**. Now it has a real job: packing the backpack. This robot is born at `(250, 250)`, the middle of a 500×500 window.

### `+=` and `-=`: shortcut operators

```java
y -= stepSize;     // same as:  y = y - stepSize;
x += stepSize;     // same as:  x = x + stepSize;
```

Read `x += 10` as "**add 10 to x**." It's just less typing.

### `private`: the diary with a lock 🔒

`private` means **only code inside the Robot class** can touch that field. Code in `Main` can't do this:

```java
robot.x = 9999;   // ❌ ERROR: x has private access in Robot
```

Why lock it? Imagine a robot with `private int battery;`. If anyone could write `robot.battery = -50;`, your robot would be in a state that makes no sense. By locking the fields, the Robot class stays **in charge of its own state**. The only way to change `x` is through methods like `moveRight()`, which always move by exactly `stepSize`.

This idea is called **encapsulation**: keep the data private and expose safe buttons (methods) to use it.

`public` is the opposite: anyone can use it. That's why the move methods are `public`. They're the buttons we *want* people to press.

### Getters: a window in the locked door 🪟

If `x` is private, how does `Main` find out where the robot is? We add a **getter**, a tiny method that returns the field's value:

```java
public int getX() {
    return x;
}
```

`Main` can now **read** the position with `robot.getX()`, but it still can't **change** it directly. Reading is allowed; writing is not. Getters are usually named `get` plus the field name.

### `final`: carved in stone 🗿

```java
private final int stepSize;
```

`final` means "once this gets a value, it can **never** change." The constructor sets `stepSize = 10`, and from then on it's locked forever. If any method tried `stepSize = 50;`, Java would refuse to compile.

Use `final` for values that should never change while the program runs. It protects you from your own future typos.

### `toString()`: the robot's name tag 🏷️

```java
@Override
public String toString() {
    return "Robot at position (" + x + ", " + y + ")";
}
```

Every Java object secretly already has a `toString()` method. By default it returns something ugly like `Robot@1b6d3586`. We **replace** it with our own friendly version. `@Override` is a note to Java saying "I'm replacing a method that already exists on purpose. Please double-check I spelled it right."

Now we can print a robot directly:

```java
System.out.println(robot);
```

```text
Robot at position (250, 250)
```

When you print an object (or `+` it onto a String), Java calls its `toString()` for you automatically.

## `this`: "Me, Myself and I" 🙋

Sometimes a parameter has the **same name** as a field:

```java
class Robot {
    private String name;

    public Robot(String name) {
        this.name = name;
    }
}
```

Inside the constructor there are now **two** things called `name`: the field in the backpack and the parameter that was just handed in. `this.name` means "**my** field called name." So the line reads: "Put the name I was given into **my** backpack."

## 🙈 Common Oopsies

- **Declaring a field inside a method.** Then it's just a local variable, and it vanishes when the method ends. Fields go at the top of the class, outside any method.
- **Re-declaring the field in the constructor.** `int x = 250;` inside the constructor creates a *new* local `x` and leaves the field at `0`. Use `x = 250;` without the type.
- **Forgetting `this.`** when a parameter and a field have the same name. `name = name;` just copies the parameter onto itself, and the field stays `null`.
- **Trying to change a `final` field** after the constructor. Java won't allow it.
- **Typing `tostring()` or `ToString()`.** It must be exactly `toString()`. `@Override` catches this typo for you, which is one reason to always use it.
